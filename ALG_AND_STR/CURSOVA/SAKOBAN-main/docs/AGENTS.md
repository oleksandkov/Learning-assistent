# Правила роботи агентів у проєкті SOKOBAN

## Ієрархія

- Агент у кореневому worktree `main` є головним агентом-оркестратором.
- Усі агенти в дочірніх Orca worktree є субагентами головного оркестратора.
- Головний агент не реалізує програмний код, тести, ігрові ресурси або інтерфейси власноруч під час оркестрованої розробки.
- Головний агент відповідає за декомпозицію роботи, постановку задач, уникнення конфліктів, контроль результатів, координацію залежностей та інтеграцію завершених гілок.
- Субагент виконує лише явно призначену задачу у своєму worktree та не передає її іншим агентам без окремої вказівки оркестратора.

## Обов’язковий режим запуску субагентів

- За прямою вказівкою користувача всі coding-субагенти запускаються лише в provider-specific bypass-режимі, щоб вони не зупинялися на локальних permission-dialog.
- Antigravity CLI запускається з `--dangerously-skip-permissions`.
- Codex CLI запускається з `--dangerously-bypass-approvals-and-sandbox`.
- Перед запуском OpenCode або іншого agent CLI оркестратор повинен перевірити його поточний `--help` і використати точний офіційний прапорець повного bypass; вигадувати назву прапорця заборонено.
- Bypass не розширює межі задачі: субагент усе одно працює тільки у власному worktree, не змінює чужі каталоги та не виконує руйнівних операцій.
- Оркестратор повинен переконатися, що ефективна команда нового agent terminal справді містить потрібний bypass-прапорець, перш ніж передавати задачу.

## Спільний контекст

Перед початком реалізації кожен субагент повинен повністю прочитати:

- `PLAN.md` — загальну архітектуру й етапи розробки;
- `ALGORITHMS.md` — правила, алгоритми, інтеграцію ШІ та методику вимірювання часу;
- це кореневе `AGENTS.md` — межі відповідальності агентів.

Індивідуальне завдання у PDF є первинним джерелом вимог. Якщо документація суперечить PDF, субагент має повідомити оркестратору про суперечність до зміни архітектури.

## Володіння напрямами

### `sokoban-cli`

CLI-субагент створює початкову спільну програмну основу:

- кореневу CMake-конфігурацію;
- незалежне C++20-ядро в `src/core/`;
- BFS, A*, евристики та Deadlock Detection у `src/solvers/`;
- термінальний застосунок у `src/cli/`;
- benchmark runner у `src/benchmark/`;
- модульні та інтеграційні тести в `tests/`;
- контрольні XSB-рівні в `levels/`;
- технічні інструкції зі збирання і запуску.

До інтеграції цієї основи Web- і Godot-субагенти не повинні створювати альтернативні реалізації правил або алгоритмів.

### `sokoban-web`

Web-субагент працює лише після інтеграції стабільного ядра та відповідає за:

- `web/`;
- `bindings/web/`;
- Emscripten/WebAssembly-збирання;
- TypeScript, HTML Canvas і Web Worker;
- web-тести та інструкції запуску.

Web-субагент не дублює C++-правила гри й не змінює публічний API ядра без погодження з оркестратором.

### `sokoban-godot-blender`

Godot/Blender-субагент працює лише після інтеграції стабільного ядра та відповідає за:

- `godot/`;
- `bindings/godot/`;
- GDExtension-адаптер;
- Godot-сцени, GDScript, UI, анімації та звук;
- Blender-моделі й вихідні файли ресурсів у погоджених каталогах `assets/`;
- desktop-збирання й інтеграційні тести Godot.

Godot не повинен мати окрему копію правил Sokoban або solver-алгоритмів.

## Правила реалізації

- Логіка гри та пошуку має залишатися незалежною від CLI, Godot і Web API.
- Людина, AI, replay і тести надсилають команди через один публічний API `GameSession`/`GameRules`.
- BFS повинен гарантувати мінімальну кількість рухів у покроковому графі.
- A* повинен явно вказувати метрику `Moves` або `Pushes` і використовувати допустиму евристику для заявленої оптимальності.
- Deadlock Detection не повинен відкидати потенційно розв’язні стани в безпечному режимі.
- Чистий час пошуку вимірюється окремо від завантаження, preprocessing, реконструкції, валідації, UI та анімації.
- Усі знайдені рішення повторно перевіряються через правила гри перед відтворенням.
- Публічні API мають бути документованими й придатними для наступних Web та Godot інтеграцій.

## Git і межі змін

- Кожен субагент працює лише у власному worktree та власній гілці.
- Не можна редагувати файли безпосередньо в іншому worktree.
- Не можна видаляти або перезаписувати чужі зміни.
- Не можна виконувати `git reset --hard`, примусовий push або інші руйнівні Git-операції.
- Зміни мають бути поділені на зрозумілі коміти з перевіреним станом збірки.
- Перед завершенням задачі субагент повинен запустити релевантні тести й повідомити точні команди та результати.
- Якщо необхідна зміна файла, що належить іншому напряму, субагент спочатку ставить питання оркестратору.

## Звітування

- Для оркестрованої задачі субагент дотримується lifecycle-повідомлень, які Orca додає до завдання.
- У фінальному звіті потрібно вказати: що реалізовано, які файли змінено, які тести запущено, які обмеження залишилися та хеш фінального коміту.
- Блокер не приховується і не обходиться зміною архітектури без погодження.
- Після `worker_done` субагент не починає наступну задачу самостійно.

## Пріоритети

1. Коректність правил і рішення.
2. Відсутність втрати даних та конфліктів між worktree.
3. Перевірюваність і відтворювані тести.
4. Правильність метрик часу та статистики.
5. Продуктивність.
6. Зручність інтерфейсу й візуальне оформлення.
