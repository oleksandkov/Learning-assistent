# Прототип 6. Метод «Гравітаційного зливу»

## Статус і призначення

Це експериментальна концепція аналогової гідродинамічної евристики для Sokoban. Вона не є загальновизнаним точним solver-алгоритмом: фізичні образи використовуються для створення напрямку пошуку, а остаточні дії все одно виконуються дискретно через правила гри.

Рівень уявляється рельєфом:

- цілі — найнижчі точки, або «стоки»;
- стіни — непрохідні високі гори;
- підлога — поверхня зі змінною висотою;
- ящики — тіла з масою;
- віртуальне масло або вода — поле потоку з малим тертям;
- «струшування» — контрольований шум, який допомагає вийти з локальної западини.

Алгоритм не штовхає ящик буквально без участі гравця. Фізична симуляція лише оцінює бажаний напрямок, після чого GameRules перевіряє, чи може гравець стати позаду ящика і виконати відповідне штовхання.

## Представлення поля

Після одноразового розбору XSB використовуються наявні Board і GameState. Додатково будується поле потенціалу:

~~~cpp
struct DrainCell {
    double height;       // висота: менше біля цілі
    double pressure;     // накопичений потік
    double flowX;
    double flowY;
};

struct BoxBody {
    core::CellIndex cell;
    double mass;
    double velocityX;
    double velocityY;
};
~~~

Базову висоту доцільно рахувати не прямою мангеттенською відстанню, а зворотною хвилею від цілей з урахуванням стін і місця для гравця. Недосяжні клітинки отримують нескінченну висоту.

## Загальна схема

~~~mermaid
flowchart TD
    A[Board і початковий GameState] --> B[Побудувати рельєф від цілей]
    B --> C[Обчислити напрямки потоку]
    C --> D[Прикласти сили до кожного ящика]
    D --> E[Запропонувати спадні штовхання]
    E --> F{GameRules дозволяє штовхання?}
    F -- Так --> G[Виконати найкраще штовхання]
    F -- Ні --> H[Відхилити або струсити поле]
    G --> I[Оновити рельєф, енергію і стан]
    H --> I
    I --> J{Усі ящики на цілях або вичерпано енергію?}
    J -- Ні --> C
    J -- Так --> K[ReplayValidator]
~~~

## Один цикл симуляції

1. Для кожного ящика визначаються чотири можливі напрямки.
2. Для сусідньої клітинки обчислюється перепад висоти:

   ~~~text
   slope = height[current] - height[next]
   ~~~

3. До оцінки додаються тиск потоку, інерція та штрафи:

   ~~~text
   force =
       slope * gravity
       + pressure[next]
       + inertia
       - playerApproachCost
       - collisionPenalty
       - deadlockPenalty
   ~~~

4. Варіанти сортуються за force.
5. Найсильніший варіант перевіряється через досяжність гравця та GameRules.
6. Якщо жоден спадний рух неможливий, карта отримує короткий випадковий «струс»: напрямок сили трохи повертається, але заборонені ходи не дозволяються.

## Примітивний псевдокод

~~~text
terrain = reversePushDistances(goals, walls)
state = initial
energy = Emax
history = []

поки energy > 0 і state не є ціллю:
    candidates = []

    для кожного box:
        для кожного direction:
            force = downhillForce(box, direction, terrain, flow)
            якщо гравець може стати позаду box
               і GameRules дозволяє push:
                candidates.додати(box, direction, force)

    якщо candidates порожній:
        змінити shakeVector
        energy -= shakeCost
        продовжити

    action = кандидат з найбільшою force + контрольований шум
    state = виконати action через GameRules
    оновити flow, velocity та зайняті клітинки
    history.додати(state, action, force, energy)
    energy--

перевірити знайдений маршрут через ReplayValidator
~~~

## Приблизна інтеграція з програмою

~~~cpp
auto terrain = buildReversePushTerrain(board);
core::GameState state = initial;
std::vector<core::Direction> moves;

for (std::size_t tick = 0; tick < maxTicks && !state.isGoal(board); ++tick) {
    auto pushes = legalPushes(board, state); // reachability + GameRules
    scoreByDrainForce(pushes, terrain, flow, shakeVector);
    if (pushes.empty()) {
        shakeVector = rotateWithSeed(shakeVector);
        continue;
    }
    const auto chosen = bestForce(pushes);
    appendPlayerApproachAndPush(state, chosen, moves);
}
~~~

Фізична модель не повинна обходити GameRules. Вона замінює лише порядок вибору кандидатів і може використовуватися як евристика в A*, beam search або локальному пошуку.

## Візуалізація у вебі

1. **Карта висот.** Цілі показані синіми лунками, стіни — темними піками. Колір клітинки відповідає height.
2. **Потік.** Тонкі стрілки показують напрямок віртуальної рідини. Яскравість відповідає pressure.
3. **Сили ящика.** Біля вибраного ящика відображаються чотири вектори; заборонені перекреслюються після перевірки GameRules.
4. **Струшування.** Короткий нахил усього рельєфу пояснює, чому алгоритм тимчасово вибрав не найнижчий напрямок.
5. **Енергія.** Графік показує потенційну, кінетичну енергію та найкращу відому оцінку.
6. **Чесний replay.** Окремий режим відтворює тільки фактичні кроки гравця і штовхання, без фізичних декорацій.

Для кожного кадру достатньо зберігати номер tick, стан ящиків, вибране штовхання, сили кандидатів і енергію. Повні копії поля не потрібні.

## Частота сканування поля

XSB сканується один раз. Рельєф будується один раз або перебудовується лише після зміни набору вільних цілей. На кожному tick перераховуються сили для максимум 4 × кількість ящиків напрямків і досяжність гравця.

Орієнтовна складність:

~~~text
preprocessing: O(клітинки × цілі)
tick:          O(досяжні клітинки + 4 × ящики)
повний запуск: O(maxTicks × tick)
~~~

## Лімітації прототипу 6

1. **Фізична аналогія не дорівнює Sokoban.** Ящики не ковзають і не можуть рухатися без гравця.
2. **Немає гарантії розв’язку або оптимальності.** Потік може стабільно вести до нерозв’язного кута.
3. **Локальні мінімуми.** Ящик іноді треба спочатку віддалити від цілі; простий градієнт цього не розуміє.
4. **Чутливість до параметрів.** gravity, тертя, інерція, сила струшування і штрафи сильно змінюють поведінку.
5. **Кілька ящиків взаємодіють.** Один ящик може перекрити «стік» іншому, тому потрібне призначення різних цілей.
6. **Осциляція.** Без пам’яті алгоритм може штовхати ящик туди-назад.
7. **Візуалізація може вводити в оману.** Потік є евристичною підказкою, а не реальною фізичною симуляцією.
8. **Дискретна валідація обов’язкова.** Кожне показане рішення має пройти ReplayValidator.

## Рекомендований мінімальний варіант

Почати без справжньої гідродинаміки: використати зворотну карту висот, один вектор струшування і вибір найсильнішого дозволеного штовхання. Додавати тиск, швидкість і рідину варто лише тоді, коли проста потенціальна модель уже працює та має зрозумілу візуалізацію.
