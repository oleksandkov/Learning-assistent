# Прототип 4 Візуалізація Simulated Annealing у вебі

## Статус і призначення

Це пропозиція візуального прототипу фізико-математичної метаевристики для Sokoban у вебклієнті. Призначений для наочної демонстрації виходу з локальних мінімумів: як алгоритм спочатку дозволяє собі «погані» ходи, а потім поступово стає суворим.

Головна ідея: імітується охолодження металу. На високій температурі з високою ймовірністю приймаються навіть ходи що погіршують позицію (наприклад, відкотити ящик назад від цілі, щоб потім обійти його). Це дозволяє вийти з глибоких тупиків Sokoban. З охолодженням алгоритм приймає лише покращення.

Обрано серед Tabu / Harmony / Potential Fields, тому що:
- SA дає драму температури: одна крива пояснює всю поведінку;
- Tabu — це список заборон, візуально нудніший (таблиця станів);
- Harmony дублює GA (матриця пам'яті замість популяції);
- Potential Fields — другий heatmap після ACO (прототип 2), без нової картинки.

## Дані з наявної програми

Повторно сканувати поле не потрібно. Після завантаження рівня використовуються структури програми:

```cpp
initial.player;       // позиція гравця
initial.boxes;        // позиції всіх ящиків
board.goals();        // позиції всіх цілей
board;                // стіни для перевірки ходів
```

Для прототипу зберігається лише стрічка кроків:

```ts
type SATrace = { step: number; temp: number; cost: number; acceptedBad: boolean; cells: [x,y][] };
```

Валідація маршруту — як у прототипах 1–3: результат перевіряється через `ReplayValidator` або послідовні виклики `GameRules::tryMove()` перед відтворенням.

## Загальна схема

```mermaid
flowchart TD
    A[Початковий стан, T = Tmax] --> B[Згенерувати сусідній хід через GameRules]
    B --> C{Хід кращий}
    C -- Так --> D[Прийняти]
    C -- Ні --> E[Прийняти з p = exp(-delta / T)]
    E --> D
    E --> F[Відхилити]
    D --> G[Охолодити: T *= alpha]
    F --> G
    G --> H{Розв'язок або T < Tmin}
    H -- Ні --> B
    H -- Так --> Z[Зберегти SATrace для вебплеєра]
```

## Режими вебплеєра

1. **Крива + карта синхронно.** Зверху графік `temp↓` і `cost` по кроках, знизу карта. Скрабер `step`: повзунок рухає одночасно маркер на графіку і гравця на карті.
2. **Погані ходи.** Кожен `acceptedBad = true` — червоний спалах і мітка `пішов у гірше щоб вийти з тупика`. Toggle `показати тільки погані прийняття` — видно де алгоритм рятувався.
3. **Повзунок температури.** Ручний режим: крутиш `T` і бачиш ймовірність `p = exp(-delta / T)` для наступного ходу. Пояснює формулу без тексту.
4. **Порівняння охолоджень.** Два прогони з різним `alpha` (швидке/повільне): чий cost впав нижче, хто застряг. Той самий прийом `vs` що у прототипах 2–3.

Загальні контроли: play/pause, швидкість, вибір прогону, heatmap відвіданих станів on/off.

## Примітивний псевдокод

```text
state = initial
best = state
T = Tmax
trace = []

поки T > Tmin і кроків < maxSteps:
    next = випадковий допустимий сусід (GameRules)
    delta = cost(next) - cost(state)
    якщо delta < 0 або rand() < exp(-delta / T):
        state = next
        acceptedBad = (delta > 0)
        якщо cost(state) < cost(best): best = state
    інакше:
        acceptedBad = false (відхилено)
    trace.додати({step, T, cost(state), acceptedBad})
    T *= alpha

повернути trace + best
```

`cost = pushes * wP + moves * wM + distToGoals * wD + deadlockPenalty` — та сама функція що у прототипі 3.

## Приблизний каркас для програми

```cpp
core::GameState state = initial;
core::GameState best = initial;
double T = Tmax;
std::vector<SAStep> trace;

for (int step = 0; step < maxSteps && T > Tmin; ++step) {
    auto next = randomNeighbor(board, state); // тільки ходи за GameRules
    int delta = cost(next) - cost(state);
    bool take = (delta < 0) || (rand01() < std::exp(-delta / T));
    if (take) {
        state = next;
        if (cost(state) < cost(best)) best = state;
    }
    trace.push_back({step, T, cost(state), take && delta > 0});
    T *= alpha;
}
// best перевірити через GameRules перед показом, trace -> web/src (Canvas 2D)
```

## Частота сканування поля

Парсер сканує поле один раз при завантаженні рівня. Під час відпалу позиції беруться з `GameState`. Один крок — `O(1)` сусід + оцінка `cost`. Вебплеєр лише відтворює збережений `trace`, скрабер працює за `O(1)` на кадр.

## Лімітації прототипу 4

1. **Не є повноцінним solver.** SA не гарантує оптимальності; це демонстрація втечі з локальних мінімумів.
2. **Чутливість до розкладу.** Погані `Tmax/alpha` = або вічний хаос, або швидке застрягання; потрібен підбір під рівень.
3. **Випадковий сусід слабкий.** Без евристичного сусіда (тягнути до цілі) на багатоящикових рівнях блукатиме довго.
4. **Один ланцюжок.** Немає популяції як у GA; для надійності — кілька рестартів, а не один прогін.
5. **Маршрут не є дозволом на рух.** Перед показом як «розв'язок» — обов'язкова перевірка через правила гри.

## Умови, за яких прототип працює

Прототип доцільний, якщо:

- потрібна саме історія «спочатку стрибав куди попало, потім зійшовся» (крива температури + спалахи поганих ходів);
- достатньо малих/середніх рівнів з явними локальними тупиками (відкат ящика назад);
- вебклієнт (`web/src`, Canvas 2D) лише програє збережений `trace`, а не рахує відпал у реальному часі;
- результат порівнюється з baseline (прототип 1, BFS, A*) за динамікою cost, а не заявляється як оптимальний solver.
