# Алгоритми, керування та інтеграція ШІ у грі «Сокобан»

## 1. Призначення документа

Цей документ деталізує алгоритмічну частину проєкту, описаного у [PLAN.md](PLAN.md). Він визначає, як мають працювати правила Sokoban, ручне керування, автоматичний гравець, алгоритми BFS та A*, виявлення тупиків, відновлення й анімація розв’язку, а також коректне вимірювання часу.

Документ має бути одночасно:

- технічним завданням для реалізації C++-ядра;
- основою для алгоритмічних розділів пояснювальної записки;
- контрактом між CLI, Web і Godot-інтерфейсами;
- планом майбутнього розширення системи новими алгоритмами ШІ;
- переліком умов, за якими можна перевірити правильність і продуктивність програми.

Основна ідея: людина та ШІ не повинні мати дві різні реалізації правил. І ручний гравець, і автоматичний розв’язувач надсилають однакові команди до одного об’єкта `GameSession`. Це гарантує, що автоматично знайдений шлях завжди перевіряється тими самими правилами, що й рухи користувача.

## 2. Що в цьому проєкті означає «ШІ»

У межах курсової роботи основним ШІ є система інтелектуального пошуку в просторі станів. Вона аналізує поточне поле, передбачає наслідки штовхань і знаходить послідовність дій, що приводить усі ящики до цілей.

Обов’язкова основа ШІ:

- BFS як повний неінформований алгоритм і контрольний еталон;
- A* як інформований алгоритм з евристикою;
- Deadlock Detection як система логічного відсікання безнадійних станів;
- автоматичне відтворення знайденого рішення;
- режим підказки, в якому ШІ пропонує лише наступний хід;
- можливість передати керування між користувачем і ШІ без перезапуску рівня.

У майбутньому за тим самим інтерфейсом можна підключити IDA*, pattern database, навчувану евристику, reinforcement learning або зовнішній AI-сервіс. Проте жоден зовнішній модуль не отримує права напряму змінювати поле: він лише пропонує команди, а `GameRules` перевіряє їхню допустимість.

## 3. Формальна модель гри

### 3.1. Ігрове поле

Нехай поле має розмір `M × N`. Після вилучення стін залишається множина прохідних клітинок `F`. Множина цілей позначається `G`, множина позицій ящиків — `B`, а позиція гравця — `p`.

Кількість ящиків дорівнює кількості цілей:

```text
|B| = |G| = K
```

Повний стан гри задається як:

```text
S = (p, B)
```

Стіни та цілі не входять у динамічний стан, тому що вони не змінюються під час проходження рівня. Вони належать статичному об’єкту `Board`.

### 3.2. Допустимий рух

Для напрямку `d ∈ {Up, Down, Left, Right}` позначимо сусідню клітинку як `p + d`.

Рух без штовхання допустимий, якщо:

```text
p + d ∈ F
p + d ∉ B
```

Після руху змінюється тільки позиція гравця:

```text
S' = (p + d, B)
```

### 3.3. Допустиме штовхання

Штовхання допустиме, якщо перед гравцем розташований ящик, а клітинка за ящиком є вільною:

```text
p + d ∈ B
p + 2d ∈ F
p + 2d ∉ B
```

Після штовхання:

- гравець переходить на попередню позицію ящика;
- ящик переходить на наступну клітинку;
- інші ящики не змінюють позицій.

Тягнути ящик, пересувати два ящики одночасно або штовхати ящик у стіну заборонено.

### 3.4. Цільовий стан

Рівень завершений, якщо кожен ящик стоїть на цілі:

```text
B = G
```

Оскільки кількість ящиків і цілей однакова, достатньо перевірити, що кожна позиція ящика належить множині цілей.

## 4. Представлення даних

### 4.1. Індекс клітинки

Двовимірну координату `(x, y)` доцільно перетворити на один індекс:

```text
index = y × width + x
```

Це спрощує масиви, хешування, порівняння станів і таблиці відстаней. Тип `CellIndex` бажано визначити явно, наприклад як `std::uint32_t`.

### 4.2. Статичні дані `Board`

`Board` зберігає:

- `width` і `height`;
- бітову або байтову маску стін;
- маску цілей;
- список прохідних клітинок;
- до чотирьох сусідів кожної клітинки;
- статичні мертві клітинки;
- reverse-push-відстані від клітинок до цілей;
- початковий стан рівня.

Попереднє обчислення сусідів прибирає повторні перевірки меж поля під час пошуку.

### 4.3. Динамічний стан `GameState`

Мінімальне представлення:

```cpp
struct GameState {
    CellIndex player;
    std::vector<CellIndex> boxes;
};
```

Позиції ящиків мають бути відсортовані. Нумерація ящиків не має змісту: стани з однаковим набором позицій ящиків і однаковою позицією гравця повинні бути рівними.

Для поля до 64 або 128 прохідних клітинок можна додати оптимізоване представлення через одну або декілька бітових масок. Воно дозволяє перевіряти наявність ящика майже без витрат.

### 4.4. Незмінність пошукових станів

Стан, уже доданий у `Open Set` або `Closed Set`, не змінюється. Для створення сусіда формується новий стан або копія з локальною зміною. Це запобігає пошкодженню ключів хеш-таблиці.

## 5. Єдиний механізм команд для людини та ШІ

Передбачаються команди:

```cpp
enum class Direction { Up, Down, Left, Right };
enum class CommandSource { Human, AI, Replay, Test };

struct MoveCommand {
    Direction direction;
    CommandSource source;
};
```

Усі команди проходять через один метод:

```cpp
MoveResult GameSession::apply(const MoveCommand& command);
```

`MoveResult` повідомляє:

- чи був хід допустимим;
- чи відбулося штовхання;
- яка клітинка була початковою і кінцевою;
- який ящик перемістився;
- чи завершено рівень;
- скільки часу зайняла логічна обробка команди.

Інтерфейс не змінює координати самостійно. Він лише викликає `apply()`, отримує результат і показує його. Це правило однакове для CLI, Web і Godot.

## 6. Режими взаємодії користувача та ШІ

### 6.1. Manual

Користувач повністю керує гравцем. Пошук не виконується. Кожен допустимий рух додається в історію.

### 6.2. Hint

ШІ аналізує поточний стан, але повертає лише одну рекомендовану команду або перше штовхання з поясненням. Команда не виконується автоматично, доки користувач її не підтвердить.

### 6.3. AI Step

ШІ знаходить план, але виконує рівно одну команду після натискання кнопки «Наступний крок». Користувач може аналізувати кожний етап розв’язку.

### 6.4. Autoplay

ШІ знаходить рішення та передає його у `SolutionPlayer`. Той виконує команди по черзі з обраною швидкістю анімації.

### 6.5. Compare

BFS та A* запускаються на однаковій копії початкового стану. Їхні результати не застосовуються до гри автоматично, а показуються у порівняльній таблиці. Користувач вибирає, яке рішення відтворити.

### 6.6. Takeover

Користувач може зупинити автоматичне відтворення і продовжити вручну. Невиконана частина плану вважається застарілою та відкидається. Для продовження AI-проходження запускається новий пошук від поточного стану.

### 6.7. Реакція на ручний хід під час пошуку

Пошуковий алгоритм працює з незмінною копією стану та ідентифікатором запиту. Якщо користувач змінює поле:

1. активний запит скасовується;
2. версія `GameSession` збільшується;
3. пізній результат старого запиту ігнорується;
4. користувач продовжує гру без блокування;
5. нова підказка або Autoplay починається вже від нового стану.

Це не дозволяє застосувати правильний, але застарілий шлях до іншої конфігурації поля.

## 7. Undo, Redo та історія

Історія не повинна зберігати повну копію поля після кожного руху. Достатньо запису:

```cpp
struct MoveRecord {
    CellIndex playerFrom;
    CellIndex playerTo;
    std::optional<CellIndex> boxFrom;
    std::optional<CellIndex> boxTo;
    CommandSource source;
};
```

Undo застосовує зворотну зміну. Redo повторно передає початкову команду правилам. Після нового руху користувача стек Redo очищується.

Рухи, виконані ШІ, також потрапляють в історію. Тому користувач може покроково скасувати автоматичний розв’язок і продовжити самостійно.

## 8. Простір станів як граф

Кожна вершина графа — допустимий `GameState`. Ребро — команда руху або макроштовхання залежно від алгоритму.

Для `F` прохідних клітинок і `K` ящиків груба верхня межа кількості станів дорівнює:

```text
C(F, K) × (F - K)
```

Не всі ці стани фізично досяжні, але навіть така оцінка показує комбінаторний вибух. Саме тому потрібні компактне представлення, хешування, евристика і Deadlock Detection.

Існують два корисні види графа:

- граф окремих рухів, у якому кожне ребро має вартість 1;
- граф штовхань, у якому ребро містить найкоротший шлях гравця до ящика та одне штовхання.

Перший простіший і природний для BFS. Другий значно менший і практичніший для A*.

## 9. BFS: пошук у ширину

### 9.1. Призначення

BFS є контрольним алгоритмом для невеликих рівнів. Він не використовує інформацію про розташування цілей, тому досліджує стани в порядку збільшення відстані від початку.

Якщо кожне ребро відповідає одному руху, BFS гарантує рішення з мінімальною кількістю рухів. Ця гарантія не діє, якщо одним ребром представлено штовхання разом із довільною кількістю кроків гравця.

### 9.2. Структури даних

- `std::deque<NodeId>` — черга відкритих вузлів;
- `std::unordered_map<GameState, NodeId, StateHasher>` — відвідані стани;
- `std::vector<SearchNode>` — стабільне сховище вузлів;
- `SearchNode::parent` — індекс попереднього вузла;
- `SearchNode::move` — команда, що привела до вузла.

Зберігання індексів замість вказівників спрощує серіалізацію і запобігає проблемам після розширення вектора.

### 9.3. Псевдокод

```text
BFS(start):
    queue.push(start)
    visited[start] = root

    while queue is not empty:
        current = queue.pop_front()
        explored += 1

        if is_goal(current):
            return reconstruct(current)

        for direction in [Up, Left, Down, Right]:
            next, transition = try_move(current, direction)

            if transition is invalid:
                continue

            generated += 1

            if transition pushed a box and is_deadlock(next):
                deadlock_pruned += 1
                continue

            if next is already visited:
                duplicate_pruned += 1
                continue

            save parent(next) = current
            save move(next) = direction
            visited.insert(next)
            queue.push_back(next)

    return no_solution
```

Фіксований порядок напрямків робить результат детермінованим: на однаковому рівні програма обирає однаковий шлях серед декількох однаково коротких.

### 9.4. Відновлення рішення

Після знаходження цілі алгоритм іде за батьківськими посиланнями від цільового вузла до кореня, додає рухи у зворотному порядку, а потім розвертає масив.

Повні стани шляху зберігати не обов’язково. Для кожного вузла достатньо:

- індексу батька;
- команди переходу;
- вартості або глибини;
- самого стану чи посилання на нього у сховищі.

### 9.5. Складність

Для фактично відвіданого графа:

```text
час:   O(V + E)
пам’ять: O(V)
```

У Sokoban `V` може бути експоненційним відносно кількості вільних клітинок і ящиків. Основне обмеження BFS — не швидкість однієї операції, а величезна кількість станів у пам’яті.

### 9.6. Переваги BFS

- простота реалізації і пояснення;
- повнота на скінченному графі;
- мінімальна кількість рухів у покроковому графі;
- хороший еталон для перевірки A*;
- відсутність залежності від якості евристики.

### 9.7. Недоліки BFS

- велике споживання пам’яті;
- дослідження великої кількості явно неперспективних станів;
- погана масштабованість;
- непридатність для більшості великих рівнів без сильного відсікання.

## 10. Внутрішній BFS доступності гравця

А* не повинен генерувати всі звичайні кроки як окремі глобальні стани. Для поточного розміщення ящиків запускається малий BFS лише по клітинках поля, доступних гравцю.

Результат містить:

- маску досяжних клітинок;
- найкоротшу відстань до кожної клітинки;
- батьківські напрямки для відновлення маршруту до позиції штовхання.

Після цього для кожного ящика і напрямку перевіряється:

- чи доступна клітинка, з якої гравець має штовхати;
- чи вільна клітинка, куди переміститься ящик;
- чи не створює це штовхання доведений тупик.

Таким чином, десятки звичайних кроків стискаються в один макроперехід, але повна послідовність `UDLR` зберігається для відтворення.

## 11. A*: евристичний пошук

### 11.1. Призначення

A* є основним автоматичним розв’язувачем. Він використовує оцінку відстані до мети та спочатку досліджує перспективні стани.

Для вузла `n`:

```text
f(n) = g(n) + h(n)
```

де `g(n)` — точна накопичена вартість, а `h(n)` — допустима нижня оцінка залишкової вартості.

### 11.2. Дві метрики оптимізації

#### Мінімум штовхань

Кожне макроштовхання має вартість 1:

```text
g(next) = g(current) + 1
```

Цей режим швидший, створює менший граф і є рекомендованим для складних рівнів. Рішення має мінімальну кількість штовхань, але не обов’язково мінімальну кількість кроків гравця.

#### Мінімум усіх рухів

Вартість ребра дорівнює довжині найкоротшого маршруту гравця до позиції штовхання плюс саме штовхання:

```text
edge_cost = shortest_walk_to_push_position + 1
```

Після штовхання позиція гравця однозначно дорівнює попередній позиції ящика. Тому використання найкоротшого маршруту до конкретного штовхання не втрачає кращого продовження.

Цей режим знаходить мінімум рухів за умови допустимої евристики, коректного оновлення `g` та повторного відкриття стану, якщо знайдено дешевший шлях.

### 11.3. Структури даних

- `std::priority_queue<OpenEntry>` — вузол з найменшим `f` отримує найвищий пріоритет через відповідний компаратор;
- `std::unordered_map<GameState, Cost>` — найкраще відоме значення `g`;
- `std::vector<SearchNode>` — вузли та батьківські зв’язки;
- кеш доступності гравця;
- кеш значення евристики для конфігурації ящиків.

Через відсутність операції ефективного decrease-key у стандартній `priority_queue` допускається додавання нового запису з кращим `g`. Під час вилучення застарілий запис розпізнається порівнянням із поточним найкращим `g` і пропускається.

### 11.4. Псевдокод

```text
A_STAR(start, metric):
    best_g[start] = 0
    open.push(start, f = heuristic(start))

    while open is not empty:
        current_entry = open.pop_min_f()

        if current_entry.g != best_g[current_entry.state]:
            stale_pruned += 1
            continue

        current = current_entry.state
        explored += 1

        if is_goal(current):
            return reconstruct_macro_path(current)

        reachability = player_bfs(current)

        for each legal push derived from reachability:
            next = apply_push(current, push)
            generated += 1

            if is_deadlock(next):
                deadlock_pruned += 1
                continue

            edge = cost(push, reachability, metric)
            tentative_g = best_g[current] + edge

            if next is unknown or tentative_g < best_g[next]:
                h = heuristic(next)
                if h is infinite:
                    deadlock_pruned += 1
                    continue

                best_g[next] = tentative_g
                parent[next] = current
                macro_action[next] = push with player path
                open.push(next, f = tentative_g + h)

    return no_solution
```

### 11.5. Умова оптимальності

A* повертає оптимальний результат за обраною метрикою, якщо:

- `h(n)` ніколи не перевищує справжню мінімальну залишкову вартість;
- усі вартості ребер невід’ємні;
- стан повторно відкривається, коли знайдено менше `g`;
- алгоритм завершується на коректно вилученій із черги цілі, а не просто під час її генерації;
- Deadlock Detection не має хибнопозитивних спрацювань.

## 12. Евристики для A*

### 12.1. Нульова евристика

```text
h(S) = 0
```

A* перетворюється на алгоритм Дейкстри. Цей варіант потрібний для тестування реалізації, але не для продуктивної гри.

### 12.2. Сума мангеттенських відстаней

Проста оцінка:

```text
h(S) = Σ min_goal |box.x - goal.x| + |box.y - goal.y|
```

Вона швидка, але не враховує стіни і дозволяє різним ящикам умовно обрати одну ціль. Через це оцінка дуже слабка.

### 12.3. Reverse-push-відстані

Для кожної цілі виконується зворотний пошук положення умовного ящика. Зворотний перехід дозволяється тільки тоді, коли:

- попередня позиція ящика є підлогою;
- клітинка, на якій мав би стояти гравець для прямого штовхання, також є підлогою;
- стіни не перешкоджають руху.

Інші ящики під час цього попереднього обчислення ігноруються. Отримана відстань є нижньою оцінкою реальної кількості штовхань: додаткові ящики можуть лише ускладнити шлях, але не зробити його коротшим.

### 12.4. Мінімальне призначення ящиків цілям

Формується матриця `cost[i][j]`, де елемент — reverse-push-відстань від ящика `i` до цілі `j`.

Потрібно знайти взаємно однозначне призначення:

```text
h(S) = min_assignment Σ cost[box_i][assigned_goal_i]
```

Для цього використовується Угорський алгоритм зі складністю `O(K³)`. Евристика сильніша за незалежний вибір найближчої цілі, тому що кожна ціль призначається лише одному ящику.

Якщо повне скінченне призначення не існує, конфігурація ящиків не може бути розв’язана і відкидається.

### 12.5. Кешування евристики

Значення призначення залежить від позицій ящиків, але не від точного положення гравця. Тому результат можна кешувати за канонічною конфігурацією ящиків. Це особливо корисно, коли алгоритм зустрічає однакове розміщення ящиків із різних позицій гравця.

### 12.6. Нижня оцінка першого підходу гравця

Для режиму мінімізації всіх рухів можна додати мінімальну відстань гравця до будь-якої позиції допустимого першого штовхання. Її потрібно комбінувати з box-goal-оцінкою лише після доведення допустимості, щоб сума не рахувала одну дію двічі.

У першій стабільній версії достатньо евристики призначення за штовханнями. Вона простіша для математичного обґрунтування.

## 13. Канонізація позиції гравця

У режимі мінімізації штовхань точна позиція гравця всередині однієї доступної області часто неважлива: до наступного штовхання він може безкоштовно, з точки зору метрики pushes, дійти до будь-якої клітинки цієї області.

Тому стан можна канонізувати:

```text
canonical_player = найменший індекс доступної клітинки
```

Це об’єднує багато еквівалентних станів і скорочує пошук. Фактичний шлях гравця до кожного штовхання все одно відновлюється внутрішнім BFS.

У режимі мінімізації всіх рухів таку канонізацію без додаткової інформації використовувати не можна, оскільки точна позиція впливає на наступну вартість ходьби.

## 14. Deadlock Detection

### 14.1. Вимога безпечності

Тупиковий детектор має право відкинути лише стан, для якого доведено неможливість розв’язання. Хибнопозитивний результат робить BFS або A* неповним і може приховати єдиний правильний шлях.

Евристичні, але не доведені правила можна використовувати лише в окремому режимі `aggressive`, який не заявляє гарантію оптимальності або повноти.

### 14.2. Нецільовий кут

Якщо ящик стоїть не на цілі й має стіну або незсувну межу з двох перпендикулярних боків, його неможливо вивести. Це найпростіший статичний тупик.

### 14.3. Статичні мертві клітинки

Reverse-push-пошук від усіх цілей визначає множину клітинок, із яких умовний ящик може бути доставлений хоча б до однієї цілі. Будь-яка прохідна нецільова клітинка поза цією множиною є статично мертвою.

Ця перевірка охоплює не лише очевидні кути, а й тупикові ділянки біля стін і неправильні закінчення коридорів.

### 14.4. Блок 2 × 2

Якщо квадрат `2 × 2` повністю зайнятий стінами та/або ящиками, і щонайменше один ящик у ньому не стоїть на цілі, така конфігурація часто є незворотною. Реалізація повинна врахувати розташування цілей, щоб не відкидати коректний завершений блок.

### 14.5. Заморожений ящик

Ящик є замороженим, якщо його неможливо перемістити ні по горизонталі, ні по вертикалі через стіни або інші заморожені ящики. Перевірка може бути рекурсивною, але повинна мати множину вже переглянутих ящиків для уникнення циклу.

Якщо заморожений ящик не стоїть на цілі, стан тупиковий. Якщо кілька заморожених ящиків стоять на цілях, потрібно переконатися, що вони не блокують інші необхідні цілі.

### 14.6. Неможливе box-goal-призначення

Матриця reverse-push-відстаней одночасно є детектором тупика. Якщо для деякого набору ящиків неможливо побудувати повне призначення різним цілям, рівень із такого стану не розв’язується.

### 14.7. Corral deadlock

Corral — область, до якої гравець не може потрапити через ящики. Аналіз таких областей може знаходити складні тупики, але є дорогим і складним. Його слід залишити оптимізацією другої черги після стабілізації BFS, A* і базових перевірок.

### 14.8. Коли запускати перевірку

Розташування ящиків змінюється лише після штовхання, тому динамічний Deadlock Detection не потрібно запускати після звичайного кроку. Порядок дешевих і дорогих перевірок:

1. локальний кут або dead square;
2. локальний блок `2 × 2`;
3. freeze-перевірка;
4. перевірка повного призначення;
5. розширені corral/tunnel-правила.

## 15. Хешування та перевірка рівності

### 15.1. Звичайний хеш

На першому етапі використовується комбінація хешу позиції гравця та всіх відсортованих позицій ящиків. Рівність завжди перевіряється за повними даними стану.

### 15.2. Zobrist hashing

Для кожної пари «клітинка — тип об’єкта» за фіксованим seed генерується 64-бітне число. Хеш стану утворюється XOR-комбінацією відповідних чисел.

Переваги:

- швидке інкрементальне оновлення після руху;
- рівномірний розподіл ключів;
- зменшення вартості роботи `Closed Set`.

Zobrist-хеш не є доказом рівності. Через теоретично можливу колізію хеш-таблиця повинна додатково порівнювати повний канонічний стан або використовувати 128-бітну комбінацію з повною перевіркою.

Фіксований seed забезпечує відтворюваність тестів і результатів профілювання.

## 16. Відновлення та перевірка знайденого рішення

Результат алгоритму має містити:

```cpp
struct Solution {
    std::vector<Direction> moves;
    std::uint64_t moveCount;
    std::uint64_t pushCount;
    OptimizationMetric optimizedFor;
};
```

Для A* кожен macro-action містить:

- шлях гравця до клітинки за ящиком;
- напрямок штовхання;
- батьківський стан.

Після відновлення макрошляху всі локальні маршрути об’єднуються у звичайний рядок `UDLR`.

Перед передаванням рішення інтерфейсу ядро обов’язково виконує його на копії початкового стану через `GameRules`. Рішення приймається лише тоді, коли:

- кожна команда допустима;
- підсумковий стан є цільовим;
- фактична кількість рухів і штовхань відповідає метаданим;
- початковий state/version збігається із запитом.

Цей фінальний replay-validator захищає від помилок відновлення батьківських зв’язків.

## 17. Інтерфейс розв’язувачів

Базовий контракт:

```cpp
class ISolver {
public:
    virtual ~ISolver() = default;

    virtual void start(
        const Board& board,
        const GameState& state,
        const SolverOptions& options) = 0;

    virtual SearchStatus advance(std::size_t nodeBudget) = 0;
    virtual void requestCancel() = 0;
    virtual SolverProgress progress() const = 0;
    virtual SearchStatistics statistics() const = 0;
    virtual std::optional<Solution> solution() const = 0;
};
```

Можливі значення `SearchStatus`:

- `NotStarted`;
- `Running`;
- `Solved`;
- `NoSolution`;
- `Cancelled`;
- `LimitReached`;
- `InvalidLevel`;
- `InternalError`.

`SolverOptions` містить:

- алгоритм;
- метрику `Moves` або `Pushes`;
- ліміт часу;
- ліміт досліджених станів;
- приблизний ліміт пам’яті;
- набір увімкнених deadlock-перевірок;
- режим детермінованого tie-breaking;
- частоту публікації прогресу.

## 18. Асинхронне виконання без зависання інтерфейсу

### 18.1. CLI

У командному benchmark-режимі алгоритм може виконуватися синхронно. В інтерактивному режимі пошук запускається у `std::jthread`, щоб користувач міг його скасувати.

### 18.2. Godot

Godot передає ядру незмінний snapshot. Пошук працює у фоновому потоці та не звертається до вузлів сцени. Прогрес передається через потокобезпечну чергу повідомлень. Зміни UI, сигналів і сцени виконуються тільки в головному потоці Godot.

### 18.3. Web

WebAssembly solver працює у Web Worker. Основний JavaScript-потік відповідає за Canvas, клавіатуру та анімацію. Обмін відбувається повідомленнями зі станом прогресу або готовим рішенням.

### 18.4. Кооперативний режим

Додатково всі алгоритми підтримують `advance(nodeBudget)`. Якщо потоки недоступні, UI викликає цей метод раз на кадр і задає обмеження кількості вузлів. Пошук залишається переривним і не блокує інтерфейс надовго.

## 19. Коректне вимірювання часу

### 19.1. Чому одного показника недостатньо

Загальний час натискання кнопки «Solve» включає читання рівня, підготовку таблиць, пошук, відновлення шляху, передавання між потоками та оновлення UI. Якщо все назвати «часом алгоритму», порівняння буде некоректним.

Потрібно окремо вимірювати:

```text
level_load_time       — читання та перевірка XSB;
preprocessing_time    — dead squares і таблиці reverse-push;
search_time           — власне цикл BFS або A*;
reconstruction_time   — побудова повного шляху;
solution_validation_time — повторна перевірка рішення;
total_solver_time     — сума підготовки, пошуку і завершення;
logical_move_time     — виконання одного правилами гри;
animation_active_time — фактична тривалість активної анімації;
playback_wall_time    — повний час відтворення з паузами;
input_response_time   — затримка від введення до оновлення стану/кадру.
```

Для вимоги курсової «чистий час пошуку» використовується саме `search_time`. У таблицях додатково показуються `preprocessing_time` і `total_solver_time`, щоб оптимізація не приховувала витрати в іншій фазі.

### 19.2. Монотонний годинник

У C++ використовується:

```cpp
using Clock = std::chrono::steady_clock;
```

`system_clock` не підходить, оскільки системний час може змінитися через синхронізацію, часовий пояс або ручне налаштування.

У Godot для UI-анімації використовується монотонний лічильник ticks, а у браузері — `performance.now()`. Внутрішній WebAssembly-пошук використовує монотонне джерело часу, доступне через Emscripten/`steady_clock`.

### 19.3. Одиниці та точність

Внутрішня тривалість зберігається цілим 64-бітним значенням у наносекундах або мікросекундах. Перетворення в мілісекунди виконується тільки для відображення:

```text
0.184 ms
27.531 ms
1 284.902 ms
```

Не слід округлювати кожен проміжний інтервал окремо. Спочатку сумуються точні значення, потім формується показник.

### 19.4. Межі `search_time`

Таймер чистого пошуку запускається безпосередньо перед додаванням початкового стану в `Open Set` і зупиняється після встановлення фінального статусу `Solved`, `NoSolution`, `Cancelled` або `LimitReached`.

До `search_time` входять операції, які є частиною алгоритму:

- вилучення та додавання у чергу;
- генерація переходів;
- внутрішній BFS доступності в A*;
- обчислення евристики;
- перевірка тупиків;
- робота `Closed Set`.

До нього не входять:

- файлове введення;
- створення спрайтів;
- відображення прогресу;
- штучні затримки;
- анімація;
- збереження CSV/JSON;
- попереднє обчислення, яке однаково повторно використовується кількома запусками, якщо воно окремо позначене як preprocessing.

Якщо певна таблиця створюється заново лише для конкретного алгоритму, її час необхідно або включити в `total_solver_time`, або явно показати окремим стовпцем.

### 19.5. Час одного логічного ходу

Для кожного допустимого `GameSession::apply()` вимірюється тільки час перевірки правил та оновлення стану. Статистика зберігає:

- мінімум;
- максимум;
- середнє арифметичне;
- медіану або percentile `p50`;
- `p95` для виявлення рідкісних затримок.

Недопустимі команди можна вимірювати окремо, оскільки їхня обробка коротша.

### 19.6. Час анімації одного ходу

Анімаційний таймер запускається в момент фактичного початку tween/transition і зупиняється в callback завершення. Пауза гри не додається до `animation_active_time`.

Показник:

```text
average_animation_time = sum(active_animation_durations) / animated_move_count
```

Окремо показується запланована тривалість, наприклад `100 ms`, і фактична медіана. Якщо фактична тривалість значно більша, це свідчить про падіння FPS або блокування головного потоку.

### 19.7. Затримка ручного керування

Для оцінювання чутливості гри вимірюється час від реєстрації input event до першого кадру, на якому почався відповідний візуальний рух. Це UI-метрика, а не час алгоритму.

Логічне застосування команди повинно бути практично миттєвим. Візуальна тривалість може бути більшою для плавності, але не повинна створювати відчуття затримки. За потреби наступний ввід буферизується.

## 20. Методика чесного порівняння BFS та A*

### 20.1. Однакові умови

Порівнюються:

- однаковий початковий стан;
- однакова Release-збірка;
- однаковий комп’ютер і фонове навантаження;
- однакові ліміти пам’яті й часу;
- однакова версія Deadlock Detection, якщо досліджується саме різниця пошуку;
- однакова метрика оптимізації або чітко позначені різні метрики.

Не можна без пояснення порівнювати BFS, що мінімізує рухи, з A*, який мінімізує штовхання, лише за довжиною шляху.

### 20.2. Прогрівання

Перед серією вимірювань виконується один прогрівальний запуск, який не входить у результат. Це зменшує вплив завантаження коду, кешів і початкових системних витрат.

### 20.3. Повторення

Швидкі рівні запускаються щонайменше 10 разів. Для довгих запусків допускається 3–5 повторень. Основний показник — медіана; додатково наводяться мінімум, максимум і стандартне відхилення.

### 20.4. Вимкнення візуалізації

Під час benchmark:

- не малюється поле;
- не виводиться прогрес кожного вузла;
- не запускається анімація;
- логування накопичується мінімально або вимикається;
- результат записується лише після завершення вимірюваної ділянки.

### 20.5. Ліміти

Алгоритм має коректно завершитися зі статусом `LimitReached`, якщо перевищено:

- `timeLimit`;
- `nodeLimit`;
- `memoryLimit` або контрольний розмір структури;
- зовнішній запит скасування.

Перевищення ліміту не слід показувати як «розв’язку немає». Це різні результати.

## 21. Статистика пошуку

```cpp
struct SearchStatistics {
    SolverKind algorithm;
    OptimizationMetric metric;
    SearchStatus status;

    std::uint64_t generatedStates;
    std::uint64_t exploredStates;
    std::uint64_t duplicatePruned;
    std::uint64_t deadlockPruned;
    std::uint64_t staleQueueEntries;
    std::uint64_t reopenedStates;
    std::uint64_t maxFrontierSize;

    std::uint64_t solutionMoves;
    std::uint64_t solutionPushes;

    Duration preprocessingTime;
    Duration searchTime;
    Duration reconstructionTime;
    Duration validationTime;
    Duration totalSolverTime;

    std::uint64_t estimatedPeakBytes;
};
```

Потрібно чітко визначити лічильники:

- `generatedStates` збільшується після створення допустимого переходу до перевірки дубліката;
- `exploredStates` — після вилучення актуального вузла та перед його розширенням;
- `duplicatePruned` — коли стан не покращує відомий результат;
- `deadlockPruned` — коли стан відкинуто доведеною deadlock-перевіркою;
- `maxFrontierSize` — найбільша фактична кількість записів у черзі;
- `reopenedStates` — стан уже розглядався, але знайдено дешевший шлях.

Однакові визначення мають використовуватися у CLI, Godot, Web, CSV і пояснювальній записці.

## 22. Що краще: BFS чи A*

| Критерій | BFS | A* |
|---|---|---|
| Простота | Найпростіший | Складніший |
| Повнота | Так, за достатньої пам’яті | Так, за коректної реалізації |
| Оптимальність | Мінімум рухів у покроковому графі | Мінімум обраної метрики з допустимою евристикою |
| Використання знань про цілі | Ні | Так |
| Пам’ять | Дуже велика | Велика, але зазвичай менша фактично |
| Робота на малих рівнях | Відмінна | Відмінна |
| Робота на середніх рівнях | Часто повільна | Основний вибір |
| Робота на складних рівнях | Часто вичерпує пам’ять | Значно краща, але також не гарантує швидкого результату |
| Навчальна цінність | Еталон неінформованого пошуку | Демонстрація евристик і оптимізацій |

Висновок:

- BFS кращий як проста доказова база, перевірка правильності та пошук мінімальної кількості рухів на малих рівнях;
- A* кращий як стандартний AI-гравець для реального використання;
- A* з макроштовханнями, reverse-push-відстанями, Угорським алгоритмом і Deadlock Detection має бути алгоритмом за замовчуванням;
- на дуже великих рівнях у майбутньому варто додати IDA*, оскільки він використовує менше пам’яті, хоча може повторно досліджувати стани.

## 23. Детермінованість

Для однакових вхідних даних і параметрів алгоритм повинен повертати однаковий результат. Для цього:

- використовується фіксований порядок напрямків;
- Zobrist seed є фіксованим;
- для однакових `f` у A* застосовується tie-breaker: менше `h`, потім менший номер вставлення;
- паралельний режим не змінює порядок логічного пошуку у benchmark-збірці;
- параметри й версія програми записуються разом із результатом.

Детермінованість спрощує налагодження, повторення експериментів і захист курсової роботи.

## 24. Майбутня інтеграція складнішого ШІ

### 24.1. Реєстр алгоритмів

Замість умов `if (algorithm == ...)` використовується `SolverRegistry`, який створює реалізацію за ідентифікатором:

```text
bfs
astar
idastar
pattern-db
learned-heuristic
remote-ai
```

Новий алгоритм реалізує `ISolver` і автоматично отримує сумісність із CLI, Godot та Web за умови підтримки платформи.

### 24.2. IDA*

IDA* виконує ітеративний пошук у глибину з порогом `f`. Його головна перевага — значно менше використання пам’яті. Недолік — повторне дослідження однакових частин дерева. Він є природним третім алгоритмом після BFS та A*.

### 24.3. Pattern Database

Pattern database попередньо зберігає точні або сильні нижні оцінки для підмножини ящиків. Вона може суттєво покращити A*, але потребує окремої генерації, пам’яті та обґрунтування допустимості.

### 24.4. Навчувана евристика

Модель машинного навчання може оцінювати перспективність стану або порядок штовхань. Для збереження гарантій оптимальності навчена оцінка не повинна безпосередньо замінювати допустиму `h`, якщо вона може переоцінювати. Безпечні варіанти:

- використовувати модель лише як tie-breaker;
- використовувати її для порядку генерації сусідів;
- запускати окремий швидкий неоптимальний режим;
- поєднувати з класичним A* і чітко позначати втрату гарантій.

### 24.5. Зовнішній AI-сервіс

Зовнішній сервіс отримує серіалізований snapshot і повертає список напрямків або штовхань. Перед виконанням кожна команда перевіряється локально. Передавання рівня в мережу має бути добровільним, а відсутність мережі не повинна заважати ручній грі або локальним BFS/A*.

### 24.6. Пояснення рішення

Майбутній модуль може додавати до ходу пояснення:

- «цей ящик потрібно вивести з кута першим»;
- «ця клітинка є статично тупиковою»;
- «ціль праворуч зарезервована для нижнього ящика».

Пояснення не змінює рішення і зберігається як необов’язкова метаінформація.

## 25. Інтеграція з CLI

## 28. Помилки й граничні ситуації

Програма повинна відрізняти:

- некоректний файл рівня;
- уже завершений початковий стан;
- доведено нерозв’язний стан;
- відсутність рішення після повного пошуку;
- перевищення ліміту;
- ручне скасування;
- застарілий результат після зміни стану;
- внутрішню помилку;
- недостатню пам’ять.

Для кожного випадку UI показує зрозуміле повідомлення. Частково знайдений шлях не видається за повний розв’язок.

## 29. Перевірка правильності алгоритмів

### 29.1. Тести правил

- рух у вільну клітинку;
- блокування стіною;
- штовхання одного ящика;
- заборона штовхати два ящики;
- ящик і гравець на цілі;
- перемога після останнього штовхання;
- Undo/Redo для руху і штовхання.

### 29.2. Тести BFS

- рівень із відомим найкоротшим рішенням;
- декілька однаково коротких шляхів;
- нерозв’язний малий рівень;
- відсутність повторного розширення стану;
- коректна кількість рухів і штовхань.

### 29.3. Тести A*

- `h(goal) = 0`;
- евристика не перевищує точну відстань на малих рівнях, знайдену BFS;
- A* з `h = 0` узгоджується з Дейкстрою;
- кращий шлях повторно відкриває стан;
- макрошлях розгортається у допустимий `UDLR`;
- режими Moves і Pushes не змішують метрики.

### 29.4. Тести тупиків

Для кожного правила потрібні позитивні й негативні приклади. Особливо важливі негативні приклади, в яких схожа конфігурація все ж розв’язується. Це захищає від хибного відсікання.

### 29.5. Диференційне тестування

На всіх малих рівнях рішення A* у режимі Moves порівнюється з BFS. Якщо вартості відрізняються, це означає помилку евристики, вартості макроребра, повторного відкриття або відновлення маршруту.

## 32. Критерії готовності алгоритмічної частини

Алгоритмічну частину можна вважати завершеною, якщо:

- ручні, тестові та AI-команди проходять через однакові правила;
- користувач може в будь-який момент грати самостійно;
- Hint не виконує хід без підтвердження;
- Autoplay можна призупинити, продовжити або передати людині;
- після ручної зміни старе рішення не виконується;
- BFS знаходить мінімум рухів на контрольних рівнях;
- A* знаходить оптимум за явно вибраною метрикою;
- кожне рішення повторно перевіряється ядром;
- базовий Deadlock Detection не має хибнопозитивних результатів на тестовому наборі;
- алгоритм можна скасувати без пошкодження гри;
- UI залишається чутливим під час пошуку;
- `search_time` не містить рендеринг, анімацію або файлове введення;
- час підготовки, пошуку, реконструкції, логічного ходу та анімації показується окремо;
- benchmark повторюваний і працює у Release-конфігурації;
- CLI, Godot і Web однаково відтворюють один `Solution`;
- статистика має однозначні визначення та експортується у CSV/JSON.

## 33. Підсумкова рекомендація

Для демонстраційного й основного режиму слід використовувати A* з макроштовханнями, reverse-push-відстанями, мінімальним призначенням ящиків цілям та безпечним Deadlock Detection. Він дає найкращий баланс швидкості, якості рішення і навчальної цінності.

BFS необхідно зберегти як обов’язковий другий алгоритм, математично зрозумілий еталон і засіб перевірки оптимальності на малих рівнях.

Головний архітектурний принцип — один `GameSession` для людини та ШІ. Завдяки цьому користувач може грати сам, просити підказку, передавати керування A*, зупиняти автоматичну гру, скасовувати AI-ходи та знову продовжувати вручну.

Час потрібно показувати не одним нечітким числом, а окремими фазами. Основним академічним показником є чистий `search_time`, тоді як `total_solver_time`, `logical_move_time`, `animation_active_time` та `input_response_time` пояснюють реальну швидкодію всієї гри.
